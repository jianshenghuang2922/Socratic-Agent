### v1.1.1 背景取景调整（角色露出）

用户要求「把图片整体移动让角色多露出一些」。**先量后调，不靠猜**：
用 ffmpeg 把首帧导成 192×108 的 raw RGB，逐列算亮度 —— 角色亮部在画面 **36%~65%**（峰值 50%），含深色头发的完整轮廓约 **31%~79%**。

结论：角色横跨大半屏，而内容列 880px 居中，两者必然重叠；`object-position` 横向只有 160px 余量，推不动她。

**最终方案**（`globals.css` 的 `.bg__video`）：
```css
object-position: 100% center;
transform: translateY(6%) scale(1.22);
transform-origin: 100% 50%;
```
以**右边缘为原点**放大 —— 缩放本身产生向左位移 `(1-S) × (右边缘 - 角色位置)`，且右边缘固定不动不会露底。S=1.22 时角色左缘从 401px 移到 98px，头部进入左侧留白区，其余压在玻璃面板下被虚化，形成前后层次。`translateY 6%` 防止放大后头顶被吸顶栏切掉。

**对比过的档位**：S=1.20 最稳，1.35 过大（角色占满左半屏、头顶被切），translateY 12% 会把她压到卡片旁边显得局促。窄屏（≤720px）cover 由高度决定、角色本就占满宽度，单独收敛为 `translateY(6%) scale(1.16)` + `object-position: 45%`。

同时把暗角中心从 50% 左移到 30%，避免把角色压暗；`prefers-reduced-motion` 的静态降级改为 `background-size: 122% / position 100% 52%` 复现同样取景。

**验证**：1920 / 1440 / 1280 / 390 四档分辨率 + 完整交互流程截图确认，控制台零报错。

### v1.1.2 内容居中 + 得分模块

**背景**：这份 CSS 里存在过一段「宽屏构图」代码（`--content-bias: 0.78`，`@media (min-width: 1024px)`），把内容列右推 436.8px 给角色让位 —— 用浏览器实测门卡中心在 **757**，而视口中心是 720，确实偏了 37px。用户要求改为居中，已整段删除。

- 位置：控制条右端（`margin-left: auto`），即内容区右上角；窄屏自动换行右对齐
- 计分：`POINTS_PER_CORRECT = 5`，仅**完全答对**才加分（简答题「部分正确」不计分）
- 计数：`questionCount` 在 `requestNextQuestion` 成功时自增（= Agent 累计出题数）
- 反馈：加分时 `pulsing` 触发一次高亮（用时间戳而非布尔值，否则连续加分无法重复触发）；状态栏同时提示「回答正确 · +5 分」

**踩坑**：`pulsing` 若用布尔值，连续两次加分不会重新触发 CSS 过渡，必须用递增的时间戳/计数器作为 effect 依赖。

## 后端四个 API 实现 + 前端接入真实后端（v1.2）

### 服务端分层（`src/server/`）

- `config.ts` —— `llmConfig()` 凭据回落链 `OPENAI_API_KEY → CODEBUDDY_API_KEY → CODEBUDDY_AUTH_TOKEN`；`limits` 集中所有阈值。`cloneTimeoutMs` 因 `CLONE_TIMEOUT_SECONDS` 已按用户要求从 .env 删除，改为代码内常量 `180_000`。
- `http.ts` —— `ApiError`（带 status）、`readJson`、`requireString`、`toErrorResponse`、`describeNetworkError`。
- `llm.ts` —— 纯 fetch 调 OpenAI 兼容 `/chat/completions`，零 SDK 依赖；`extractJson()` 剥代码围栏后截首个 `{` 到末个 `}`。
- `store.ts` —— 内存会话表挂 `globalThis.__socraticStore`（**关键**：Next dev 热重载会清空模块级变量，挂 globalThis 才能存活）。`StoredContext.answers` 是 `Map<questionId, AnswerKey>`。
- `retrieve.ts` —— `tokenize`（CJK 二元组 + 拉丁词）/ `chunk` / `selectRelevant` / **`pickWindow`**（本轮新增，按轮次滚动取窗口）。
- `sources/web.ts` —— `htmlToText` + `assertPublicHost`（SSRF 防护：拒绝内网/本机）。
- `sources/repo.ts` —— `git clone --depth 1 --single-branch --no-tags` + 文件价值打分（README +1000 / 配置 +800 / 入口 +500 / `/src/` +300 / `/test` −200 / 按深度 −10）。
- `prompts.ts` —— `summarizeHistory` 抽出 `askedQuestions`（近 12 题）与 `recentTurns`（近 6 轮）；四个场景的提示词，均要求「只输出 JSON、不要代码围栏」。

### 路由（`src/app/api/agent/*/route.ts`，全部 `runtime = 'nodejs'`）

| 路由 | 请求体 | 响应 | maxDuration |
|---|---|---|---|
| `context` | `{ url }` | `{ contextId, url, kind, title, summary, size }` | 300 |
| `ask` | `{ contextId, question, history }` | `{ answer }` | 120 |
| `question` | `{ contextId, mode, history }` | `{ id, type, prompt, options? }` | 120 |
| `grade` | `{ contextId, type, questionId, selectedIndex \| question, answer }` | `ChoiceGrade \| ShortGrade` | 120 |

状态码约定：**400** 参数错 / **410** 会话或答案键失效 / **502** 上游或模型输出不合规。

### 核心设计决策

1. **答案键服务端留存**：`correctIndex` / `explanation` / `reference` 只进 `store` 的 Map，**绝不下发前端**。已用测试断言 `q.correctIndex === undefined && q.explanation === undefined`。
2. **`contextId` 藏在 `HttpAgentClient` 实例内部**：`initContext` 拿到后存私有字段，后续请求自动带上 —— `AgentClient` 接口无需为「会话 id」开洞，页面层零改动。
3. **选择题判分不调 LLM**：直接比对服务端答案键，零成本、零延迟、判定确定。
4. **简答题必须调 LLM**：参考答案只在服务端，模型批改后返回 verdict + 点评 + reference。
5. **出题三个坑，逐个堵**（`question/route.ts`）：
   - 模型不返回合规 JSON / 下标越界 → `parseChoiceDraft` 抛 502，外层重出（最多 3 次）。
   - **模型无视「不要重复」的提示** → 用 `tokenize` 算题干词元重合率，`>= 0.6` 判为重复，抛 502 重出。**这是实测发现的真问题**：光靠提示词，模型会原样重复上一题。
   - 每次都盯着资料开头出题 → `pickWindow(content, askedQuestions.length + attempt*3, budget)` 滚动窗口，逼它换区段。
6. **推理模型陷阱**：推理 token 计入 `max_tokens`，预算给小了 `content` 直接是 `null`、内容落在 `reasoning` 字段。`chat()` 默认 `maxTokens: 3000`，并对 `finish_reason === 'length'` 且存在 reasoning 的情况给出明确报错。
